### 决策与发现

- **JUCE 的 `processBlock` 缓冲是「就地」约定，不是「输入后面接输出」**。这是这一批最大的一坑：
  `AudioProcessor::processBlock` 给的缓冲宽度是 `max(输入通道数, 输出通道数)`，
  前 `输入` 个通道是输入，插件把结果写回**前** `输出` 个通道。第一版按「输入通道之后接输出通道」
  写，于是插件把声音写在 0/1 通道、我们去读 2/3 通道，听到的是静音；自建测试插件还因此越界，
  以 `0xC0000005` 崩在 `VCRUNTIME140.dll` 里。JUCE 文档与源码都确认了正确写法，
  改在 `HostedEffectPlugin::prepare` / `process` 与测试插件两处。
  （为此 `crash.log` 现在会多写一行 `module=`，下次崩了能立刻知道是谁。）
- **推子前**：插入链按 Cubase 的 Inserts 语义放在音量 / 声像之前，所以拉音量调的是
  「效果器之后的输出」。单测用一种「效果器看到的信号不随音量变、而输出跟着音量变小」的写法钉住它
  （只比输出分贝是分不出先后顺序的，增益是可交换的）。
- **试听声部与节拍器不过链**：它们是监听辅助，不是作品内容。
- **跳转时重置效果器**（切掉延迟 / 混响的尾巴），循环回卷不重置——否则「跳过去还听见跳之前的声音」。
- **不做延迟补偿**，只在行上显示插件自报的 latency（用户的选择）：整条轨道回拉会牵动
  模板与播放头的对齐，收益与复杂度不成比例。
- **工厂只在轨道真的有槽位时才被问**：`buildSchedule` 只对 `track.effects` 里的槽发问，
  所以单测里忘了加槽，假效果器就不会被调用（踩过一次）。

## 第二十批：窗口都开在屏幕里（用户反馈修复，已完成）

### 反馈

用户在**别的电脑**上运行时反馈：「很多窗口看不到，按钮都在屏幕外了」。

### 找到的原因

三处都用了 `juce::Component::centreWithSize`，而它**只居中、不看屏幕大小**
（要看屏幕的是 `TopLevelWindow::centreAroundComponent`，它才走 `constrainedWithin`；
`centreWithSize` 直接 `setBounds (parentArea.getCentreX() - w / 2, ...)`）。于是：

1. **主窗口**：`centreWithSize (1460, 950)`，而 `setResizeLimits (1120, 720, ...)` 的最小高度
   是 720。1366×768 的笔记本（工作区 1366×728）勉强装得下，但**开了 Windows 缩放的机器**
   上工作区只有 1280×672（150%）或 1093×582（125%）——窗口比屏幕高，底部整条走带栏
   （播放 / 音频设置 / 导出）落在屏幕外，而且**最小高度 720 大于那台机器的工作区**，
   窗口被约束器顶住，用户连手动拉进来都做不到。
2. **插件窗口**：只钳了位置（上一批为 Kontakt 加的），没钳尺寸；插件界面比屏幕大时，
   窗口的右下角永远在屏幕外。
3. **音色窗口**：`centreWithSize (780, 560)`，同样不检查屏幕；屏幕矮的时候面板底部
   （试听键盘 / 鼓垫）被切掉，而且没有任何办法看到。

### 修法

- 新增 `Source/Core/WindowPlacement.h/.cpp`（两个目标都编译，纯几何可单测）：
  `usableArea`（留 8 px 边距，永不为空）→ `placeWindow`（放不下先缩，再整体挪进工作区，
  放得下保持居中）→ `fitMinimum`（最小尺寸随屏幕降低）→ `displayAreaFor`（窗口开在
  **它所属窗口所在的那块屏幕**上，副屏不会被弹回主屏）。主窗口要的 1460×950 与
  1120×720 也搬进这个模块当常量，自检直接拿它们算。
- 主窗口、音色窗口、插件窗口、插件选择器全部改走它；导出对话框里的轨道列表高度按
  屏幕高度收（`AlertWindow` 自己会把高度钳在屏幕内，但列表不让位就会把按钮顶出窗口）。
- **窗口被压小之后内容改成滚动**，而不是裁掉：
  - 插件界面放进 `Viewport`，界面本身保持插件自报的尺寸（超出窗口的部分滚动可达）；
  - 音色窗口的面板恒为 780×560 的设计尺寸，窗口更小就滚；
  - 插件界面自己改尺寸时，窗口长到**屏幕允许的那么大为止**（原来是无上限地长）。
- 插件窗口只在**第一次打开**时居中；已经在屏幕上的窗口只被约束、不被搬走
  （否则插件加载完成时那次 `refresh()` 会把用户摆好的位置拉回屏幕中央）。

### 决策与发现

- **`centreWithSize` 不会因为屏幕小就缩小或挪位**，这是这一批的全部原因。JUCE 里唯一
  会做「挪进父区域」的是 `TopLevelWindow::centreAroundComponent`（`AlertWindow` 走的是
  这一条，所以对话框类窗口本来就没事），HM 自己的三个 `DocumentWindow` 都绕过了它。
- **光把窗口改小会把内容裁掉**——那只是把「够不到的按钮」换成「不存在的按钮」。
  所以插件界面与音色面板用滚动，而按钮在下方的窗口（选择器 / 导出框）则让中间那部分
  先让位（列表滚动、树缩小）。
- **最小尺寸必须跟着屏幕降**：主窗口的约束器是「用户能拉到多小」的下限，它大于工作区时
  窗口会被顶回屏幕外，用户自己也没法救。
- 自检里对**真实屏幕**断言（而不是写死 1920×1080）：`displayAreaFor(nullptr)` 问出当前
  工作区，再断言窗口落在里面；同时用假的 1366×728 与 1280×672 两块屏把「小屏 / 缩放」
  这两种情况钉死，免得只有开发机那一种分辨率被测到。

### 验证

基线（旧值 → 新值）：单元测试 **26 组 / 1882 条 → 27 组 / 1906 条**，
离屏自检 **609 项 → 625 项**（快照仍然是 38 张，这一批不加图）。

- 单元测试新增 `WindowPlacement` 组（5 个用例 / 24 条断言）：放得下保持尺寸并居中、
  放不下缩到工作区（1366×728 上 1460×950 → 1366×728 从 (8,8) 起算）、副屏（负坐标）
  留在副屏、工作区比留白还小时给出 ≥1×1、最小尺寸随屏幕从 720 降到 656（有地方时不动）。
- 离屏自检新增一节「每个窗口都开在屏幕里」（16 项）：主窗口在真实工作区里、最小尺寸不超过
  它、1366×728 与 1280×672 两块假屏的推算、音色窗口外框在屏幕里且面板保持 780×560、
  强行缩到 520×380 后面板不变形并出现滚动、插件窗口在屏幕里且界面保持插件自报尺寸、
  插件改成 1200×320 后窗口只长到屏幕允许的大小、选择器拿到 600×520 或整个工作区且按钮
  留在窗口里。
- 交付物由 `work\make_release.bat` 重出。

## 第二十一批：插件列表真的显示出来（用户反馈修复，已完成）

### 反馈

用户在插件选择器里反馈：「在外接乐器和效果器里看不到扫描后的内容」——
状态行扫完写着「扫描完成：找到 N 个 VST3 插件」，列表却一片空白。

### 找到的原因

第十九批第一步把选择器从平铺列表改成 `juce::TreeView` 时，**`RootItem` 的构造函数是空的**：

```cpp
    explicit RootItem (PluginPicker& ownerToUse) : owner (ownerToUse)
    {
    }                     // ← 分组算好了，但一条也没加进控件
```

`GroupItem` 的构造里会给分组挂插件行，可是**从来没有人构造过 `GroupItem`、也没有人把它
`addSubItem` 到根上**，所以树永远是空的。扫描、缓存、缓存重载、分组、搜索全都正常，
只有「把结果放进用户看得见的控件」这一步从来没有发生。

**为什么自检没抓到**：那一批新增的所有钩子读的都是选择器旁边的数据
（`visible` / `groups` / `closedGroups`）——`getVisibleCountForTest()`、
`getGroupTextForTest()`、`getShownPluginCountForTest()`、`setGroupOpenForTest()` 全是，
连快照也只是拍下来、没人去数列表区域。于是「数据完全正确、控件完全空白」这套组合
在 578 → 625 项全绿的检查下安然通过。这是这一批最值得记住的一条。

顺带抓出第二个：`GroupItem` 原来用 `setOpen(! owner.closedGroups.count(...))` 记住折叠状态，
但 `juce::TreeViewItem::setOpen(false)` 在**还没挂到树上**的 item 上是**空操作**——
`isOpen()` 在 `ownerView == nullptr` 时恒为 false，于是「关掉」这个动作没被记下来，
分组一重建就自己弹开。改成 `setOpenness (Openness::opennessClosed)` 显式存状态。

### 修法

- `RootItem` 的构造函数按分组填树：有名字的加 `GroupItem`，「不分组」的那一组把插件行
  直接挂在不可见的根下（和列表语义一致）。
- 折叠状态改成 `setOpenness (Openness::opennessClosed)`（只对关掉的分组存显式状态）。
- 空列表不再是一块空白：`paintOverChildren` 里居中写一句
  「还没有找到插件：点「重新扫描」扫一遍标准 VST3 目录，或者用「添加目录…」把插件所在的目录
  加进来。」；搜索框里有字且没命中时写「没有名字里带「X」的插件。」
- 顺手修掉扫描回调的悬空捕获：选择器是对话框的内容组件、关窗即被删除，而后台扫描结束会在
  消息线程回调 `rebuild()`。改成 `juce::Component::SafePointer`（`--添加目录…` 的
  文件选择回调同理）。
- **自检改成数真实控件**（这条比前面的修复更重要）：
  - `getTreeItemCountForTest()`：递归数树里到底有多少 item；
  - `getTreeVisibleRowCountForTest()`：去掉折叠分组后真正会画出来的插件行数；
  - 树区域的**非背景色像素**（新增 `countNotColour` 辅助函数）——空树就是一块纯背景；
  - 断言三重对齐：控件行数 == 数据行数、折叠 / 展开时两个数字一起变、像素 > 200；
  - 再加一条**走真实扫描结果**的用例：`scanFolderNow` 扫进测试插件 → 建选择器 →
    断言它列出 ≥1 条且树里真有行（前面那些用例喂的是假列表，覆盖不到用户真正走的路径）。

### 验证

## 第二十二批：插件界面不再互相追尺寸（用户反馈修复，已完成）

### 反馈

用户反馈：「插件界面有时会混乱或无法控制」。

### 找到的原因

「有时」这个限定词是关键——它只在插件**自己改尺寸**时才发作。上一批为了让「屏幕装不下
插件时还能滚动」把插件**总是**放进 `Viewport`，于是 `layoutEditor()` 变成：

```cpp
    const auto width  = juce::jmax (editorNativeSize.x, viewport.getMaximumVisibleWidth());
    const auto height = juce::jmax (editorNativeSize.y, viewport.getMaximumVisibleHeight());
    editor->setBoundsConstrained ({ 0, 0, width, height });   // ← HM 替插件发明了一个尺寸
```

再加上 `componentMovedOrResized` 会把插件的新尺寸回推给窗口（`onEditorSizeChanged` →
`setSize`），就形成了**双向耦合**：

- 插件尺寸 ← 窗口尺寸（上面那两行 `jmax`）
- 窗口尺寸 ← 插件尺寸（`componentMovedOrResized`）

会自己吸附到固定档位的插件（Kontakt 的缩放大步、Serum 的 constrainer）拿到一个不是它要的
尺寸后会自己再设回去，窗口又跟着变，再算一次 `jmax` 又给出另一个尺寸……两边一直互相改，
表现就是界面花掉、正在动画的控件点不中（「混乱 / 无法控制」）。

第二个问题在 `refresh()`：

```cpp
    setSize (juce::jmax (getWidth(),  content->getPreferredSize().x),
             juce::jmax (getHeight(), content->getPreferredSize().y));   // ← 只增不减
```

插件**永远不能把自己变小**：Kontakt 把缩放调小、或者换成紧凑面板时，窗口拒绝变小，
于是 `jmax` 又把它撑回原来的大小，等于把上面的互追钉死在原地。

### 修法

- **插件永远拿自己的尺寸**：`layoutEditor()` 里装得下就是普通子组件
  （`setBoundsConstrained (窗口内区)`，和没有视口时一模一样），装不下才进 `Viewport`，
  而且进去以后**只给插件自己的尺寸**——HM 不发明尺寸。
- **视口只在「界面比窗口大」时启用**（新增 `setScrolling()` 负责搬家），
  所以常见情况走的是和以前完全一样的那条路径。
- **`componentMovedOrResized` 改成边沿触发**：尺寸没变就直接返回（排版不是插件改主意），
  并且**滚动期间不再把窗口尺寸回推给插件**——窗口已经在屏幕允许的最大值，
  再追只会继续打架。
- **`refresh()` 两个方向都跟着插件走**（去掉 `jmax`），插件能把自己改小。

结果：尺寸链变成**单向**（插件 → 窗口），一遍就收敛。

### 验证

基线（旧值 → 新值）：离屏自检 **637 项 → 644 项**（单元测试仍是 27 组 / 1906 条，快照 38 张）。

- 新增 7 项，关键的四条（都是「只有插件自己改尺寸时才发作」的路径，必须当回归用例）：
  `the window shrinks when the plugin does (400x300)`（老代码会拒绝变小）、
  `and nothing keeps resizing anything (400x300 / 400x300)`（连跑 8 圈消息循环，
  尺寸一个像素都不再变——互追就会在这里抖）、
  `an interface bigger than its window is scrolled` +
  `and it keeps the size the plugin asked for (900x600)`（窗口被强行缩到 400×300 时，
  界面保持自己的尺寸、窗口不被推回）、
  `while the window stays where the screen put it (400x300)`（滚动期间插件再长大，
  窗口也不动）。
- 交付物由 `work\make_release.bat` 重出。
