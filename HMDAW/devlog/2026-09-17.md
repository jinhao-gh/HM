# 2026-09-17 开发日志

## 第二十六批：四个用户报告的缺陷（已完成）

### 完成

**1. 框选时弹出音符编辑栏会挤压画布 → 抖动**

- 根因：`EditorPanel::refresh()` 每次选中变化都以 `resized()` 收尾，而音符编辑栏只在
  「有选中」时占高度（单选 62 px / 多选 34 px + 逐音符列表最多 92 px）。框选过程中选中数
  一直在变 → 画布高度反复变 → y↔频率映射跟着变，音符在指针下跳，拖动中算出的频率也错。
- 改法：`NoteEditBar::slotHeight`（= 单选那档 62 px）成为**固定槽位**，`EditorPanel::resized()`
  每次都切出它，画布拿剩下的高度（**不再随选中变化**）；多选时的逐音符列表改成
  **压在画布上方的浮层**（栏的 bounds 越过槽位 + `toFront()`）；没选中时栏隐藏、槽位里画一行
  淡字提示（「选中音符后，可以在这里改频率 / 力度 / 备注」）。

**2. 片段头不在零点时：写音符显示错位、拖长度位置错乱**

- 根因：两处「相对 tick / 绝对 tick 混用」。音符的 `startTick` 相对片段，视图映射是绝对的：
  （a）写入预览把绝对 tick 塞进 `Note`，而 `noteRect()` 又加一次 `clipStartTick()` → 预览偏一个片段头；
  （b）`updateResizePreview` 拿绝对的指针 tick 去和相对的 `resizeOriginalStart/End` 比，
  画与提交时又各减一次片段头 → 位置乱。
- 改法：（a）预览的 `startTick` 减掉 `clipStartTick()`；（b）改长度/改起点那条路**统一成绝对**：
  捕获原始起止时加 `clipStartTick()`，画与提交处的减法保持不变；
  `getDragPreviewEndTickForTest()` 去掉多余的那次加法。

**3. 打开工程后乐器栏（行头）显示不对**

- 根因：`TrackArea::changeListenerCallback` 只 `repaint()`，**不重建行头**；`openProject()`
  也没刷新 → 加载新工程后行头还是上一个工程的（名字 / 类型 / 按钮全不对）。
- 改法：`headersMatchTracks()` 抽出「id 是否一致」，change 回调在不一致时重建（一致时不重建，
  避免抢焦点）；新增 `TrackArea::reloadForNewProject()`（**强制**重建 + 纵向偏移归零 + 重排），
  并把 `openProject` 的加载逻辑抽成 `MainComponent::loadProjectFile()`（文件选择器与自检都走它），
  里面同时 `appState.selectClip (0)`——新旧工程的片段 id 都从 1 开始，不清理片段竖栏会显示上一个工程的片段。

**4. 轨道多了以后行头被编辑栏挡住（够不到「音色」按钮）**

- 根因：音轨栏没有纵向滚动，`laneBounds()` 直接用 `序号 × 86 px`，超出可见高度的轨道够不到。
- 改法：`TrackArea` 加 `laneScroll`（像素偏移，`laneBounds()` 减去它，`resized()` 里夹到两端），
  `mouseWheelMove` 改成 **滚轮 = 纵向滚动**（向上滚 = 看上面的轨道，与编辑栏纵向滚轮同向）、
  **`Shift` + 滚轮 = 横向平移**（原来的滚轮行为）、**`Alt` + 滚轮 = 横向缩放（不变）**。
  按用户的选择**不画滚动条**，纵向只靠手势。

### 决策与发现

- **画布高度恒定是从根上消除这一类抖动**：只要「布局随状态变」，映射就会跟着变，拖动中算出的
  频率/落点都会漂。用固定槽位 + 浮层换掉「按需撑高」之后，选中与否、选中几个，画布的
  bounds 与映射都一模一样。
- **相对 / 绝对 tick 混用是这批两个 bug 的共同根**（预览、改长度）。修法是**让一条路径内部单位一致**，
  而不是在每个使用点补加减——改长度那条路整体用绝对 tick，画与提交处的减法就成了唯一一处换算。
- **自检里写音符必须先让片段在视野里**：`setBothTimelines` 的横向偏移要设到片段头附近，
  否则 `mouseDown` 会因为点落在画布外直接 return（第一版用例就是这么红的）。
- **参考线要 `locked`**：未锁定的手输线在解析时不会出现，自检里造线要按保存工程里的样子设 `locked = true`。
- **行头列不是音轨栏的点选目标**：行头是子组件，自检点轨道要点**行内容**（`headerWidth` 之后）。

### 验证

基线（旧值 → 新值）：单元测试 **27 组 / 1922 条 → 27 组 / 1922 条**，
离屏自检 **658 项 → 687 项**（38 张快照，本批不加图）。

- 四组新自检（29 项）全绿：画布 bounds 在 0 / 1 / 2 个选中下逐字段相同、固定槽位等于单选那档、
  多选列表越过槽位；片段头在第 3 小节时写入预览与提交的矩形逐点相同、改长度预览终点等于指针 tick；
  工程切换后行头类型文字跟着换、片段选中清空、纵向偏移归零；14 条轨道下裸滚轮只改纵向（两端夹住、
  能点中滚到视野里的轨道）、`Shift` + 滚轮只改横向、`Alt` + 滚轮仍缩放。
- 交付物由 `work\make_release.bat` 重出。

## 第二十七批：再修三个用户报告的缺陷（已完成）

### 完成

**1. 重命名后无法退出命名状态**

- 根因：`LaneHeader` 的轨道名 `TextEditor` 只处理了 Return 与失焦（`onReturnKey` / `onFocusLost`），
  **没有 Escape**；而且 `applyName()` 应用完不交还键盘焦点——点音轨栏（本身不可聚焦）时焦点
  仍留在输入框里，看起来就「退不出命名状态」。
- 改法：加 `onEscapeKey` → `cancelNameEdit()`（还原原名并交还焦点）；`applyName()` 结尾也交还焦点；
  `TrackArea::mouseDown` 先把当前聚焦的**子组件**的焦点交还（点音轨栏空白处即可结束改名的输入状态）。

**2. 上下滚动时车道画到上方工具条上（图层不对）**

- 根因：行头是 `TrackArea` 的**直接子组件**，滚动后它们的 y 会跑到车道区之上，
  而子组件在父组件范围内不受裁剪——于是盖住了「＋ 新建轨道」条、节拍标记轨与标尺；
  车道本身的底色与片段也会跟着画上去。
- 改法：新增 `lanesHolder` 容器，**大小正好等于车道区**（`0, lanesTop(), 宽, 车道区高`），
  行头改成它的子组件（坐标相对它换算），容器负责裁剪；`TrackArea::paint()` 里的车道绘制
  也 `reduceClipRegion` 到车道区。

**3. 多选音符一起改长度**

- 之前只有**被拖的那一个**音符改长度（移动是整组、改长度是单个）。现在改长度与改起点
  **整组一起改**：把所有选中音符的「被拖的那条边」平移同一条 delta（delta 先按整组夹住：
  任何音符不得短于一个吸附单位、左边缘不得越过零点），预览逐个音符画、提交一条撤销记录。

### 验证

基线（旧值 → 新值）：单元测试 **27 组 / 1922 条 → 27 组 / 1922 条**，
离屏自检 **687 项 → 701 项**（38 张快照）。

- 三组新自检（14 项）全绿：Return 应用改名 / Escape 取消并还原；14 条轨道滚动一格后
  「＋ 条 + 节拍标记轨 + 标尺」那块区域**逐像素不变**（0 个像素变化）；两个选中音符里拖一个的
  右边缘，另一个的时长**同幅增长**，且一次撤销把整组恢复。
- 构建零 `\Source\` 警告 ✓。两批的交付物在第二十八批收尾时**一起**由 `work\make_release.bat` 重出
  （这一步以前没跑过：第二十七批改完源码但交付物还是上一版的 exe，本次一并补上）。

### 两条「没定位」的跟进 → 第二十八批里定位并修掉

## 第二十八批：导出用插件当前状态 + 缺插件不再导静音文件 + 插件界面不重建（已完成）

### 完成

**1. 导出渲染的是插件「现在」的状态，而不是上次存盘时的状态**

- 根因：`MainComponent::runExport` 里的插件解析、工厂与 `ExportTask` 用的都是
  `document.getProject()`，而文档里的 `track.vst.stateBase64` **只在存盘时**
  （`writeProject` → `captureStates`）才被填。于是「建一条 VST 轨 → 插件里选好音色 →
  **没有存盘** → 直接导出」这条最常见的路径上，离线实例拿到的是**空状态**，
  只能按插件的**出厂音色**渲染；采样器（Kontakt 这类）的出厂音色就是空机架，
  导出文件因此没有声音，而界面上什么也不说（用户反馈的「我无法导出音频」）。
- 改法：`runExport` 一开始就在**消息线程**上取一份工程副本并
  `pluginHost.captureStates (copy)`，之后描述解析、工厂与渲染都用这份副本；
  **文档本身不动**（它的状态仍然只在存盘时更新，不产生撤销记录）。

**2. 缺插件的轨道不再被悄悄导成静音文件**

- 同一条「静音文件」现象还有第二个来源：`findDescription` 找不到插件时工厂返回空，
  调度里那条轨就是静音，导出照样写文件、还报「导出完成」。
- 改法：解析循环里顺便记下**这次要写出、且真的会出声**（没被静音 / 在勾选范围内）却解析不到
  插件的轨道与插入槽；有任何一个就直接让导出失败，错误里列出「轨道名 + 效果器名」并提示去点
  「插件界面」重新定位。被静音或未勾选的轨道不算（用户没要它的声音）。

**3. 插件界面不再因为「别的插件加载完了」而重建**

- 根因：宿主对**每一个**加载完的插件都会走一次 `onInstrumentChanged`，而
  `PluginWindow::Content::showCurrent` 无条件 `destroyEditor()` + `createEditorAndMakeActive()`。
  所以「同时开两条 VST 轨，打开 A 的界面，再让 B 加载完」就会把 A 的界面拆掉重建：
  插件在自己的数值回来之前先画一遍（推子、旋钮全在零位），缩放与滚动位置也一并丢掉——
  这正是用户报的「插件界面有时会混乱或无法控制」与「内置的音量调节会归为零」。
- 改法：`Content` 记住界面正在显示的那个实例（`shownInstance`），目标实例没变就只重排布局、
  不拆编辑器；换了插件（或插件消失、要回到提示文字）才重建。

### 验证

基线（旧值 → 新值）：单元测试 **27 组 / 1922 条 → 27 组 / 1922 条**，
离屏自检 **701 项 → 712 项**（38 张快照，本批不加图）。

- **导出那条是对着声音测的**：真插件轨导出两次，中间把插件自带音量从 0.5 拧到 0.25，
  两次干声 RMS 必须正好 2:1（`0.1085 → 0.0543`）。把 `runExport` 里的
  `pluginHost.captureStates (project)` 临时注释掉重跑，这条立刻变成 `0.1085 → 0.1085` 而失败——
  先证明了它抓的是真行为，再改回来。
- **缺插件那条**：拒绝导出（`runExport` 返回 false）、错误文字里出现轨道名、一个文件都没写；
  把那条轨静音之后，错误变成「没有勾选任何要导出的内容。」而不是报插件。
- **界面那条**：`refresh()`（宿主通知每个插件加载完成时走的正是这条路）之后，
  `getEditorForTest()` 还是同一个指针。
- 构建零 `\Source\` 警告 ✓（顺手补掉了第二十七批那三处 `grid` / `lanes` / `trackId` 的变量遮蔽
  警告——它们是上一批加的用例带进来的，因为当时没有跑完一次真正的全量构建所以没被闸门拦住）；
  交付物由 `work\make_release.bat` 重出。

### 决策与发现

- **「只在存盘时抓插件状态」这个设计本身没错，错的是导出复用了文档那份副本**：
  文档里存的应当是「用户上次存盘时听到的东西」，而导出要的是「现在听到的东西」。
  两者用同一个 `Project` 就会打架；分开成「文档」与「这次的副本」之后各归各位。
- **静音失败比报错更糟**：老代码在这条路上什么都不说（导出成功、文件没有声音），
  用户只能怀疑软件坏了。凡是「本应参与却缺席」的东西，都要在产品里说出来。
- **全局通知 + 无条件重建 = 用户界面被别人的事件重置**：`onInstrumentChanged` 是全局的，
  窗口却不是。判据要用「我显示的那个实例有没有变」，而不是「有没有事情发生」。
- **`\Source\` 警告闸门只在真正跑过全量构建之后才算生效**：第二十七批的用例带进来三处
  变量遮蔽，因为没有跑 `build_app.bat` 所以一直没被拦；这次全量重建时被抓住并修掉。

## 第二十九批：车道交互 + 插件音量/状态 + 扫描进程隔离（已完成）

### 完成

**1. 点击车道空白跳到改名 / 车道整个没反应**

- 根因（两个叠在一起）：上一批为了让行头不画到上方工具条上，把行头搬进了 `lanesHolder`，
  而它是个**普通 `Component`**——JUCE 里这种组件**默认吃掉落在它身上的所有鼠标事件**。
  于是行头右边那块车道画布的点击 / 拖动 / 滚轮全部到不了 `TrackArea`（建片段、拖片段、
  框选、滚轮滚动一起失效）；同时 JUCE 在「点到不想要键盘焦点的组件」时会把焦点交给
  **第一个可聚焦子控件**，也就是某条轨道的名字输入框（还带全选）——用户看到的就是
  「点空白跳进重命名」。
- 改法：`lanesHolder.setInterceptsMouseClicks (false, true)`（容器自己不挡、子控件照收），
  并让 `TrackArea` 与 `LaneHeader` 各自 `setWantsKeyboardFocus (true)`：点击画布/行头空白时
  焦点落在它们自己身上，JUCE 不会再去挑「默认子控件」。点名字框本身仍然是就地改名。

**2. 插件自己的音量被改**

三条宿主侧真路径：

- **滚轮改音量**：`juce::Slider` 默认响应滚轮，行头里的音量/声相推子正好在「滚轮找轨道」的
  必经之路上，滚一下就把轨道电平写进工程（还留下一条撤销记录）。改法：
  两个推子 `setScrollWheelEnabled (false)`，滚轮按 JUCE 默认一路上抛到 `TrackArea`，
  于是整条音轨栏（含行头）都是「滚轮 = 滚动轨道」。
- **重建实例时把过期状态推回插件**：文档里的 `stateBase64` 只在存盘时更新，
  而任何重新创建实例的动作（删除轨道后撤销、打开工程）都会拿它去喂插件——从没存过盘就是空，
  采样器于是回到空机架 / 出厂音色，音量自然「归零」。改法：
  （a）`TrackArea::deleteTrackNow` 在 `forgetTrack` **之前**做一次派生编辑把该轨插件的当前状态
  抓进工程（撤销回来还是刚才那个声音）；（b）新增 `PluginHostManager::resetForProject()`，
  打开/新建工程时丢掉所有活着的实例（`generation` 让在途的异步加载作废），每条 VST 轨都按
  **文件里的状态**重建——修「开工程后音量/音色是上一个工程的」；
  （c）`forgetTrack` 改成**只摘掉归属、不销毁实例**（实例继续活在 `loads` 里），
  这正是类注释一直承诺的行为，也顺手消掉了「插件窗口的编辑器比插件活得久」的隐患。
- **设备重启时的总线重排**：`prepare()` 原来每次都会重新申请总线布局，
  而 `setBusesLayout` 在 VST3 里意味着 `deactivate` → `activate`，Kontakt 这类插件会因此
  重建自己的引擎（音量被重置的来源之一）。改法：`layoutApplied` 标志，布局**只申请一次**，
  之后（音频设备重启触发的 `prepareAll`）只更新采样率 / 块大小。
- **顺手收紧 MIDI**：RPN 0 之后补 **RPN null**（CC 101/100 = 127），`allNotesOff()` 只发给
  **确实接着音符的通道**（原来无脑刷 16 个通道）。
- **可诊断**：新增 `%APPDATA%\HMDAW\plugin-events.log`（上限 512 KB），只从消息线程记宿主动作
  ——建/毁实例、`prepare`、总线布局结果、状态写入/抓取（字节数 + 哈希）、`forgetTrack`、
  `resetForProject`。以后再出现「音量被改」，这个文件能直接回答「HM 有没有动过它」。

**3. 插件扫描不再带倒 HM（子进程隔离）**

- 根因（实测）：把自检指向 `C:\Program Files\Common Files\VST3`（里面装着 Kontakt 8 / Serum2 /
  FabFilter）时，HM 在**扫描那一步直接退出了进程**（`crash.log` 为空，插件端还打了一句
  `system_info` 报错）。扫描是**在进程内加载别人的 DLL**，坏插件有权力带走宿主。
- 改法：**用同一个 HM.exe 做子进程**（不新增交付文件）。`HM.exe --scan-plugin <file> --scan-out <xml>`
  时 `main()` 先解析命令行，命中就只跑扫描子进程并 `std::_Exit`：不建窗口、不初始化音频、
  不碰 `%APPDATA%`；读一个文件、把结果写成 XML、立刻离开进程。
  父进程只做**枚举**（`searchPathsForPlugins`，不加载），然后**每个文件起一个子进程**
  （默认 30 s 超时，`ChildProcess::kill()`；子进程崩溃 / 超时 / 没写结果 = 该文件记
  「读取失败」，扫描继续）；`describeFile`（工程里点名了缓存里没有的插件、加载一个插入槽）
  也走同一条子进程路径。协议抽到 `Source/Core/PluginScanProtocol.{h,cpp}`（两个目标都编译）。
- 两处自检开关：子进程可以按 `--scan-plugin-fail-for-test` 「装死」、按
  `--scan-plugin-hang-for-test` 「装卡」，父进程必须照常跑完并把这两个文件记成失败。

### 验证

基线（旧值 → 新值）：单元测试 **27 组 / 1922 条 → 28 组 / 1981 条**，

- **「容器只用来裁切」必须显式写出来**：`Component` 默认吃鼠标，`lanesHolder` 这种纯容器
  忘了 `setInterceptsMouseClicks (false, true)` 就会把整个画布变成死区，而且**自检里的合成事件
  直接调 `TrackArea::mouseDown`，从命中测试那一层就绕过去了**——所以这次补的断言是
  `getComponentAt()` 而不是再调一遍 `mouseDown`。教训与第二十一批「数真实控件」同源。
- **焦点不能留给「猜」**：点击不想要焦点的组件时 JUCE 会把焦点交给第一个可聚焦子控件。
  画布类组件要么自己 `setWantsKeyboardFocus (true)`，要么接受光标随时跑进某个输入框。
- **`Slider` 默认抢滚轮**：任何「滚轮用来滚动/缩放」的界面里，处在路径上的 `Slider`
  都会顺手改值。凡是把滚轮交给容器的面板，都要显式关掉滑条的滚轮。
- **插件状态只有「存盘时」一份是不够的**：文档那份状态代表「上次存盘时听到的东西」，
  而任何重建实例的动作都需要**现在**的状态。删除前抓一次、导出前抓一次（上一批）、
  打开工程时按文件重建（这一批），三处合起来才是完整的一套。
- **扫描必须和宿主隔开进程**：这不是「防御坏插件」的洁癖，而是这台机器上**已经发生过**的事
   （带 Kontakt / Serum / FabFilter 的标准目录一扫就退出进程）。用同一个 exe 做子进程
   （隐藏开关）既能隔离，又不用改交付物（仍然只有一个 exe）。
- **取消标志不能跨扫描残留**：`cancelScan()` 只是「让正在跑的扫描停下来」，
  所以每次扫描开始时都要清一次——第一版没清，结果一次「选器关闭」就把之后所有
  单文件读取（`describeFile`）也连坐杀掉了（自检立刻抓到：插件全变「找不到插件」）。
- **「坏插件」就在这台机器上，而且抓到凶手了**：把标准 VST3 目录逐个文件喂给扫描子进程，
  `Kontakt 8 Portable.vst3` **读 4 秒后访问违例退出（0xC0000005）**——它自己先打了两句
  `system_info Failed to locate 'Win32_ComputerSystemProduct'` 与
  `bmemory.cpp: DoVMLock: SetProcessWorkingSetSize(…) failed`。这就是当初把 HM 一起带走的那个插件；
  现在它只让自己那个子进程死掉，HM 把它记成一个「读取失败」继续扫
  （同一次实测里 Serum2 60 ms、Lofi Panda 4 437 ms 都正常读出来）。
  已经进过缓存的插件条目不受影响（`mergeScannedPlugins` 只增不删），所以用户之前能用的 Kontakt
  照样能用；只是「重新扫描」时会看到「N 个文件读取失败」。

## 第三十一批：导出的插件调用搬回消息线程 + 导出日志（已完成）

### 完成

- **症状**：用户第三次报「无法导出」，这次的关键细节是「**导出时未响应**」——不是报错、不是
  静音，而是消息线程被卡住（Windows 给窗口盖上「未响应」）。
- **根因**：导出的插件动作**发生在渲染线程上**。`Exporter::renderToFile` → `buildSchedule` →
  工厂 → `makeOfflineInstrument`，里面是「加载插件 → prepareToPlay → setStateInformation」，
  而 JUCE 的 VST3 宿主对 prepareToPlay / setStateInformation 有明确要求：**必须在消息线程**
  （源码里就是 JUCE_ASSERT_MESSAGE_THREAD + MessageManagerLock）。在渲染线程上做这件事，
  轻则让消息线程与渲染线程互等（窗口「未响应」），重则让真实采样器（Kontakt 这类）
  直接崩在进程里。之前的自检只用自建的小插件，它对这些很宽容，所以一直没露出来。
- **改法**：
  （a）`MainComponent::runExport` 的两个工厂把整个「建实例 + 准备 + 还原状态」用
  `juce::MessageManager::callSync` **搬回消息线程**（在消息线程上调用时它直接执行，不会自锁），
  渲染线程只负责 processBlock；
  （b）**活插件的状态捕获也挪进进度窗口**：`ExportTask::run()` 先写
  「正在准备插件状态，请稍候…」并睡 220 ms（让窗口把字画出来），再用 `callSync` 在消息线程上
  捕获状态——以前这一步在主窗口里、没有任何提示，采样器一大就是「点导出 → 整窗卡死」；
  （c）每个插件的离线实例在准备前把状态文字改成「正在准备插件「X」…」，慢的插件于是在屏幕上
  自己报名字；
  （d）新增 `%APPDATA%\HMDAW\export.log`：Ctrl+E 的每一步都写进去（对话框打开没有、设置是什么、
  选了哪个文件夹、开始渲染、准备哪个插件、实例成没成、写了几个文件、失败原因），
  **每行都写在动作之前**，所以卡住时最后一行就是卡在哪一步；
  （e）自检加了「离线实例必须在消息线程上建」的计数断言（跑满一整轮导出后必须为 0）。

### 验证

基线（旧值 → 新值）：单元测试 **28 组 / 1981 条 → 28 组 / 1981 条**，
离屏自检 **757 项 → 763 项**（38 张快照，本批不加图）。

- 自检跑完整导出后断言 `PluginHostManager::getOfflineThreadViolationsForTest() == 0`；
  导出日志里出现 `render starting`、`capturing the live plugin states`、
  `offline instance for track N (…)`、`offline instance ready` / `FAILED`、
  `render finished: N file(s) written`，失败时是 `the render failed: …`。
- 交付物由 `work\make_release.bat` 重出。

### 决策与发现

- **宿主侧的插件动作只有两个合法落点**：消息线程（建实例、准备、取 / 放状态）与音频 / 渲染线程
  （processBlock）。为了「不卡界面」把这些挪到渲染线程，正好踩在 JUCE 明确禁止的位置上——
  界面看着不卡，插件却随时可以要命，或者两边互等成「未响应」。
- **阻塞步骤要写在屏幕上**：可能花几秒以上的动作，先 setStatusMessage、睡一小会儿让窗口画完，
  再做；日志则写在**动作之前**，这样崩溃或卡死之后最后一行就是答案。

## 第三十二批：导出后把被动过的活插件放回原样（已完成）

### 完成

- **症状**（用户）：**Kontakt 8 在导出时内置音量变成 0**——导出的动作本身会改到用户正在听的
  那个实例。这正是「导出无法使用」这条反馈的最后一块：插件没崩、文件也写出来了，
  但导出之后插件声音被改了。
- **根因**：导出要为每条 VST 轨建一个**私有离线实例**，于是同一个进程里同时存在**两个** Kontakt。
  Kontakt 这类采样器在同一个进程里多开时会互相干扰（它会重建自己的引擎/乐器层），
  表现就是活着的那个实例的乐器音量掉到 0。HM 这边没有任何一处写活插件（已经逐条核对过：
  捕获状态是只读的，MIDI 只发弯音范围与 all-notes-off），所以这是**插件侧**的行为，
  但能被宿主的选择影响——宿主完全可以避免在同一个进程里再开一份。
- **改法（本轮）**：导出开始时本来就把活插件的状态抓了一份（第三十一批把这件事挪进了进度窗口），
  所以导出结束后 HM **再抓一次并比较**：只要哪个实例的状态跟导出前不一样，就把它**放回原样**
  （`PluginHostManager::restoreStatesChangedSince`），并在 `export.log` 里记一行
  （`state-restored …` 或 `live plugin state unchanged by the export`）。
  渲染失败或取消也照样执行这一步——用户不该因为导出而丢掉手上的声音。
- **还没做（下一步，如果这一层不够）**：把「离线渲染插件的轨道」也搬进**子进程**
  （那样进程里永远只有一份 Kontakt）。这一层要动渲染架构，先在 devlog 里记下。

### 验证

基线（旧值 → 新值）：单元测试 **28 组 / 1981 条 → 28 组 / 1981 条**，
离屏自检 **763 项 → 769 项**（38 张快照，本批不加图）。

- 自检四步（都在真插件上跑）：① 状态没被动的实例，守卫**什么都不写**（返回 0、计数不变）；
  ② 并且插件的状态**逐字节**没变；③ 拿一份「和活实例不一样」的状态喂给它，
  守卫**检测到并写回**（返回 1、计数 +1）；④ 写回之后守卫又安静（返回 0）。
- 正常导出（测试插件）之后 `export.log` 里是 `live plugin state unchanged by the export` ✓
  ——说明 HM 自己在正常路径上不会动活插件。

### 决策与发现

- **宿主的职责是「别在同一个进程里多开」**：插件多开互相干扰是插件侧的事，
  但宿主可以选择不这么干。短期用「导出后比对 + 放回」兜住；长期的正解是离线渲染也隔离到子进程。
- **「导出后状态比对」这个手感值得保留**：它把「导出会不会改到我手上的东西」变成一条可测的
  不变量（`getLiveStateRestoresForTest()`），而不是靠用户报告。

## 第三十三批：设备重启也不再改掉插件的声音（已完成）

### 完成

- **症状**（用户）：「我在 HM 中改变音量，有时候音量又会清零」——上一次报的是**导出**时
  Kontakt 的音量归零，这次是**平时用着也会**。
- **审计**：把 HM 里所有可能写到活插件的路径逐条查了一遍——`volumeDb` / `pan` 只有行头滑条与
  工程读取会写（也就是说 HM 自己的推子没有被别处覆盖）；对插件只有「捕获状态（只读）」、
  「发 MIDI（note on/off、pitch bend、RPN 0 + null、CC 123）」与「建 / 毁实例」。
- **找到的那一条**：**音频设备重启**（`audioDeviceAboutToStart` → `prepareAll`）。采样率或
  缓冲区大小一变，插件会被 deactivate → activate 再 `prepareToPlay`，而有些采样器
  （Kontakt 最典型）在这一步会把自己重新初始化——乐器音量就回到默认 / 0。
  用户只是换了个音频设备，声音不该跟着变。
- **改法**：`prepareAll` 在「采样率或块大小真的变了」时，**先抓一份每个活插件的状态**，
  prepare 完再**把状态写回去**（并且记一行 `state-restored … (device settings changed…)`，
  计数进 `getLiveStateRestoresForTest()`）。这里是**无条件写回**而不是先比较：
  插件在 `prepareToPlay` 里的自我重置是通过参数队列告诉宿主的，这一瞬间还没送达，
  比较会看到「没变」而放它过去（第一版就是这么写的，自检立刻证明它抓不到）。
- **测试插件**跟着「学会」了这个毛病：`prepareToPlay` 里把音量重置为默认——
  这正是自检能验证这条守卫的前提。

### 验证

基线（旧值 → 新值）：单元测试 **28 组 / 1981 条 → 28 组 / 1981 条**，
离屏自检 **769 项 → 771 项**（38 张快照，本批不加图）。

- 自检：把活插件的音量设成 0.75 → `prepareAll (96000, 2048)`（真换采样率与块大小）→
  `prepareAll (48000, 1024)` 换回来 → 断言 ① 守卫**看见并处理了这次重准备**（计数增加）；
  ② 插件自己的状态**逐字节**还是用户那一份。

### 决策与发现

- **「谁把声音改了」这类问题要把两类动作分开查**：一类是 HM 的**数据**（音量 / 声像滑条——
  只有它自己和工程读取会写），一类是 HM 对**插件**的动作（取状态、发 MIDI、建 / 毁实例、
  prepare）。这次是两个不同批次的反馈分别落在这两类上，所以之前的修复看起来「没解决问题」。
- **`prepareToPlay` 对某些插件等于「重新初始化」**：宿主能做的不是阻止它，而是**在前后把用户
  的状态放回去**。这条同样适用于设备切换、缓冲区调整这些「用户没碰声音」的时刻。

## 第三十四批：模块化旋律生成器（连线即旋律，已完成）

用户的原话是「我想要像模块合成器调整音色那样连接一系列不同部件就可以生成不同旋律」，
并且要求这套交互**有探索性**（后来又要求「有游戏性」——明确说的是**交互上**的游戏性）。
所以这一批做的不是「一键生成」，而是**一张可连线的补丁**：模块、电缆、以及让试探变便宜的三条回路。

### 做了什么

- **核心（两个目标都编译、可单测）**：`Core/Patch.{h,cpp}`（8 个模块、端口信号类型、连线校验、
  拓扑求值、随机改动、JSON 往返）与 `Core/Generator.{h,cpp}`（材料 = **锁定的**参考线条目

### 决策与发现

- **补丁不进撤销栈**（D150）：探索时每秒都可能改好几次，每次都压撤销栈会把用户的真实编辑冲掉。
  派生写入 + 显式提交（`保留这一版`）是唯一能同时做到「立刻听得见」与「工程干净」的组合。
- **`Path::getNearestPoint` 返回的是「沿线的位置」不是「距离」**（JUCE 的实现返回
  `bestPosition`）：我第一版把它的返回值当距离用，于是「右键点这根线」会拔掉**另一根**
  ——判据实际变成了「离电缆**起点** 7 px 以内」。这条是**靠失败消息里的诊断数字**抓到的
  （消息里带上「哪根线被拔掉、两条线的包围盒、点在哪」，一眼就看出点落在 2>4 上、
  拔掉的却是 4>5）。已写进 `06-testing.md` 的坑清单。
- **命中测试的断言要断言「做了什么」，不能只断言「做了」**：原来那条用例只数线的条数，
  拔错线也照样通过；现在改成「拔掉的那一根 = 点中的那一根」+「接回去之后音符逐字段一致」。
- **`randomTweak` 必须是「数据结构化枚举 + 再应用」**：先枚举出所有合法改动（加模块 / 删模块 /
  接一根线 / 换一根线 / 拧一个旋钮 / 换种子），再随机挑一条真的执行，并用
  `evaluate(..., 空材料)` 复核「这仍然是一张能跑的补丁」。这样「随便按」永远不会按进死胡同。
- **本批不做**（D153）：自定义脚本模块、子补丁、导出成 VST、多轨同时生成、画布缩放与自动布局；
  调制类模块（LFO / 采样保持 / 比较器 / 延迟触发）、槽位键盘、把「游走」存成演化轨迹留给下一批。
- **一处与计划不同的地方**：计划里顶栏那个开关叫「生成后写入参考线」（含义含糊），实现里叫
  **「生成后写入片段」**：打开时每次重算都把生成的音符**派生**写进片段（所以立刻听得见），
  关掉时只画幽灵音符、必须按「保留这一版」才写。这样它和 `跟着循环听` 的分工才清楚：
  前者管「要不要写进片段」，后者管「要不要循环播放、要不要连着听改动」。
- **手工验收**：这台机器上还没有用真插件（Kontakt / Serum）走过「生成 → 导出」这条组合路径，
  留待用户在有插件的机器上试（VST 相关的验收仍按第三十三批的结论）。
