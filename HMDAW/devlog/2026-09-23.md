## 第三十九批·追加：选中多个音符 / 圆点时右键一起删（已完成）

用户接着说：「我希望在选中多个音符或圆点时，右键它们可以一起删除。」

### 做了什么

- **音符**（`Source/UI/PianoGrid.cpp`）：右键分支先 `findNoteAt`，如果命中的音符**在多选里**
  且选择不止一个，就走新的 `PianoGrid::deleteSelectedNotes()`（一次 `applyEdit("删除音符")`
  删掉整批，然后 `appState.clearNotes()`）；命中的是**没选中**的音符时仍走原来的单删。
  这条路径盖住所有音符视图（参考线模式 / 钢琴窗模式 / 鼓机格），因为它们都是同一个
  `PianoGrid`。
- **圆点**（`Source/UI/OctaveLadder.cpp`）：右键命中的圆点**在多选里**且选择不止一个时，
  把 `selectedDots` 整批交给一次 `commitGroupChange("删除圆点")`；否则和以前一样只删命中的那个。
  两个**框点**（位置 0 / 1）先被过滤掉——它们不存储、也不能删。
  因为三处（参考组栏 + 两个编辑栏）共用这个 `OctaveLadder`，所以三个地方一起生效。
- **收一处实现**：新增 `music::removeNotesByIds (Clip&, const std::set<juce::int64>&)`
  （`Core/MusicMath.{h,cpp}`），返回删掉几个。`MainComponent::deleteSelectedNotes()`
  （键盘 `Delete` / `Backspace` 走的那条）与 `PianoGrid` 的单删 / 整批删现在都用它，
  免得「键盘删」和「右键删」各写一遍 `remove_if` 之后长歪。

### 踩到的坑

- **既有自检里有一条正好撞上**：鼓机那段原来是「框选两个鼓音符 → 右键一个 → 断言那一个没了」。
  新行为下会两个一起没，所以把它改写成了整组版本（两个都没了 + 只有一条撤销 + 一次
  `Ctrl+Z` 两个都回来）——这正好是用户要的行为，不是把断言改松。
- **自检里两个 C4456**（新块里的 `grid` / `noteIds` 遮住了函数作用域里同名的变量）。
  零警告闸门会因此失败，所以改名成 `deleteNoteIds` 并改用外层的 `grid` 引用——
  单文件语法检查（`work\check_source.ps1`）先跑一遍就能当场看到。

### 数字（旧值 → 新值）

## 第三十九批·第二次追加：上下拖动碰到边界也跟着滚（已完成）

用户接着说：「我需要上下拖动时触碰边界也可以移动。」

### 做了什么

- **编辑栏的音高轴**（`Source/UI/PianoGrid.cpp` 的 `updateAutoScroll()`）：原来只有时间轴会
  跟着左右边界滚（文件里那句注释写着「只滚时间轴，纵向滚会把音高从音符底下挪走」）。
  现在纵向也滚，但**只对两种手势**（新的 `verticalScrollFollowsDrag()`）：**拖动音符**与
  **橡皮筋**。步长仍是共享的 12 px，按 `area.getHeight() / octavesVisible` 换成八度去推
  `centreHz`（`music::VerticalAxis::clampHz` 夹住），钢琴窗模式下每步之后重跑
  `alignPianoView()`（行永远是整格的），最后同样把指针钉在边界内再 `replayDragAt()`。
- **参考线模式要额外做一件事**：吸附目标 `frozenLines` 是**按下时可见的那批线**，
  不重取的话音符爬到那一批的顶就再也上不去了——那这条纵向滚动就等于白做。
  所以纵向滚动的那一步顺手 `frozenLines = currentReferenceLines()`，语义从「吸附到按下时的线」
  变成「**吸附到你现在看得见的线**」。这也是这一批里唯一一处行为语义的改动。
- **音轨栏的轨道轴**（`Source/UI/TrackArea.cpp` 的 `updateAutoScroll()`）：拖动**片段**
  （`Mode::movingClip`，唯一会换轨道的手势）时，指针碰上 / 下边界就滚 `laneScroll`，
  并且 `resized()` 让行头跟着走；滚出画面的轨道因此仍然是落点。
  建片段 / 改长度 / 拉循环不滚（目标轨道或时间点是按下时定死的）。
- 新增自检钩子 `PianoGrid::getDragRawFrequencyForTest()`（这次拖动当下会落到哪个音高），
  与已有的 `getDragRawTickForTest()` 对称。

### 踩到的坑

- **第一次跑自检，框选那条断言红了**（`440.0 Hz -> 440.0 Hz`，一个音符也没框到）。
  不是功能错，是**我写的用例自己选错了手势**：我把框选从 (x, 0.75H) 拖到 (x-150, 6)，
  横向 150 px、纵向 ~114 px，于是「第一个动作决定手势」那条规则把它判成了**写音符**
  （写音符不滚音高轴）。改成横向只走 40 px（纵向主导）之后就是橡皮筋了。
  这也提醒了另一件事：**「写音符不滚」这条是有意的**，所以它单独留了一条断言守着。
- 用例还必须**跟画布高度无关**：一次滚动大约要滑 2.6 个八度才能把画面外的 3520 Hz 音符
  送进框选带，所以步数是从 `grid.getHeight()` 算出来的，而不是写死 16 次
  （写死会在矮画布上冲过头、让音符从带子下面穿过去）。

- 离屏自检 **991 项 → 1001 项**（新块 10 项），断言与快照不变（30 组 / 2155 条、45 张）。
  实测数字：音高轴 `440 → 2847 Hz`、指针底下的音高 `1760 → 7040 Hz`、
  音轨表 `0 → 750 px`（滚到底）且片段落到 12 条轨里的第 12 条。

## 第三十九批·第三次追加：框选的角锚在内容上，不在屏幕上（已完成）

用户报告：「当我拖动到边缘时，方框边际也会跟着移动，而不是停在原地，这导致有的音符离开了框选范围。」

### 做了什么

- **根因**：框选的两个角都存在**屏幕坐标**（`marqueeStart` 是按下那一刻的 local 坐标）。
  视图一滚，屏幕固定的角相对音符就跑掉了，而 `updateMarqueeSelection()` 每次重放都按当前框
  **重算**选择 —— 于是「已经扫过」的音符又被扫出去。横向滚动其实一直有同样的毛病，只是这轮
  纵向滚动才让它显出来。
- **修法**：起框时记下按点的**内容位置**（`marqueeAnchorTick` / `marqueeAnchorHz`），
  新增 `PianoGrid::marqueeBand()`：每次按**当前视图**把角映射回屏幕（`xForTick` /
  `axis.frequencyToY`），绘制与 `updateMarqueeSelection()` 用的是同一个函数，
  所以"画出来的框"和"拿去和音符求交的框"不可能不一致。活动的那一角（指针那头）保持屏幕坐标
  ——它本来就该跟手。鼓机轨纵向是 12 个鼓垫、永不滚，那一维直接用按下的屏幕 y。

### 数字（旧值 → 新值）

- 离屏自检 **1001 项 → 1003 项**：按住时紧挨按点的音符已被框住 → **视图滚走以后它还在框里**
  （把角改回屏幕坐标，这一条会红），同时画面外的音高被框进来（最终选中 2 个）。
  断言与快照不变（30 组 / 2155 条、45 张）。
- 两个目标全量重建、零 `\Source\` 警告；`work\make_release.bat` 重出交付物。

## 第三十九批·第四次追加：从圆点或叉点旁边也能拖出框选（已完成）

用户报告：「我无法从圆点或叉点旁拖动。」

### 做了什么

- **根因**：八度线段上每个圆点 / 叉点周围有 **7 px 命中半径**（`kHitRadius`）。按在它旁边会被
  读成「点了它」，于是按下之后就 `return` 了 —— 拖动没了下文。而框选恰恰经常要从音符群
  **中间**起框（把中间那颗圆点也框进去），所以这个「点中了」的判断一直在抢框选的手势。
- **修法**：把「点击」恢复成它本来的意思 —— **按下 + 原地松手**。
    - 按在**圆点**上：照旧立刻选中它（自检与用户都依赖这个即时反馈），同时
      `bandArmedAtPress = true`、`bandKeepsPressedDot = true`；指针一动超过 3 px 就转成框选，
      并且**那颗圆点留在框里**（按它本来就是冲着它去的，框的角往往离它只有一两像素）。
    - 按在**叉点**上：**不再立刻建立圆点**，只记下 `pendingCrossValid` / `pendingCrossPosition`；
      指针一动就转成框选（顺带取消这次建立），原地松手才真正 `promoteCross()`。
      把建立圆点从按下挪到松手还顺手修掉了另一个小毛病：**误按一下不会再在工程里留下一个圆点**。
- `promoteCross()` 从 `mouseDown` 里抽出来单独一个函数，两条路（松手 / 框选期间的批量建立）读起来一致。

### 踩到的坑

- **既有自检有三处「点叉点变圆点」只发了 `mouseDown`**（它们写在「点击」只要按下就生效的年代）。
  行为改成松手生效之后，这些断言会红 —— 这是**对的行为**（一次真正的点击本来就是按下 + 松手），
  所以给它们补上配对的 `mouseUp`，而不是把行为改回去。补完之后那三条断言测的还是同一件事。

### 数字（旧值 → 新值）

- 离屏自检 **1003 项 → 1008 项**（新块 5 项），断言与快照不变（30 组 / 2155 条、45 张）。
  实测：按在圆点旁边先选中 1 个 → 拖出去框到 2 个；按在叉点上没松手时仍只有 1 个圆点 →
  拖出去之后才变成 2 个。
- 两个目标全量重建、零 `\Source\` 警告；`work\make_release.bat` 重出交付物。

  自动取景 / 删除中的任何一处 —— 它就是一次绘制 pass，所以侧视再怎么写错也动不到工程。

### 踩到的坑

- **自检第一次跑，两条断言红了**，两条都是**测试自己的问题**，不是功能的：
  ① 我用「数某个纯颜色的像素」来判断当前轨道的音符有没有被盖住 —— 但音符是**带 alpha 画上去的**，
     合成之后的颜色和纯色差很远，`countColour` 永远数到 0（`0 -> 0`）。改成「对比开关前后
     两张图，音符矩形里变化的像素必须是 0」——更准，也不依赖合成规则。
  ② 第一条大断言「变化全在幽灵矩形里」报了 3069 个越界像素。真正的原因是**坐标系**：
     幽灵矩形是画布**局部**坐标（参考线模式下画布原点就是组件原点，容易看漏），
     而我的像素扫描走的是**主窗口**坐标，两者差了一个 (216, 548) 的画布原点 —— 于是全部被判成越界。
     修掉坐标换算之后越界像素是 0。这两条都印证了库里那句老话：**断言要带诊断数字**，
     我把越界像素的**包围盒**打进消息里，一次就定位到了。
- **播放头会自己动**：快照对比之前先把走带停下来并回到 0（`audio.stop()` + `setPositionSeconds(0)`），
  否则移动的播放头会被当成「侧视多画了东西」。

## 第四十批·追加：侧视可以勾选想看的轨道（入口后来改成了小箭头）（已完成）

用户接着说：「我希望侧视可以勾选想看到的轨道。」

### 做了什么

- **右键「侧视」按钮**弹出挑轨道的菜单：第一项「显示侧视」（等于左键那一下）、
  然后**每一条能当背景的其他轨道一行**（打勾 = 要显示，点一下切换）、最后「全选 / 全不选」。
  **左键保持原样**（开 / 关）——单击是最高频的动作，不该被一个菜单拖慢。
- **不列当前轨与鼓机轨**：前者就是画布上已有的那条，后者是鼓垫不是音高；列出来只会让人
  勾了却什么都看不到。
- **存「勾掉的」而不是「要看的」**：`EditorViewState::sideViewHiddenTracks` →
  `.nprj` 的 `viewSideViewHidden`（int 数组）。于是空集合天然等于「全都看」——
  正好是这个功能做出来时的行为，旧工程不需要迁移；而且**以后新建的轨道自动在列**
  （用户的意图是「除了我特别去掉的，都给我看」）。过滤点只有一处：
  `PianoGrid::otherTrackNotes()` 里 `sideViewHiddenTracks.count (track.id) > 0` 就跳过，
  所以绘制与自检钩子看到的永远是同一份清单。
- **按钮换成 `TextButton` 的小子类 `SideViewButton`**：`Button` 的 `mouseDown` 会把右键
  也当成一次普通按下，松手就成了「点一下」——**右键会顺手把侧视关掉**。子类里右键早退、
  去调 `onPickTracks`。菜单构造与执行拆成 `buildSideViewMenu()` / `performSideViewMenuCommand()`，
  自检用 `getSideViewMenuItemsForTest()` 读菜单、用 `performSideViewMenuCommandForTest()`
  走同一条执行路径；`EditorPanel` 也学 `OptionsPanel` 加了 `showDialogs`，
  离屏自检里不真弹窗口。

### 踩到的坑

- **自检第一次跑直接崩了**（0xC0000005），三个断言报「菜单 0 项」。根因是
  `getSideViewMenuItemsForTest()` 里写成了
  `for (juce::PopupMenu::MenuItemIterator it (buildSideViewMenu()); it.next();)` ——
  **`MenuItemIterator` 存的是菜单的引用**，而 `buildSideViewMenu()` 返回的是临时对象，
  循环一开始就在读已经析构的内存。改成先存进具名局部变量（`TrackArea::getClipMenuItemsForTest`
  本来就是这个写法，照抄它就不会踩）。这条也说明「测试崩了」不一定是产品代码的错，
  但**必须查清楚**才能继续。
