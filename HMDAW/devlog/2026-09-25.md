## 第四十三批：修「声音被硬切」——插入链的尾巴 + 停止 / 循环不再掐掉释音（已完成）

用户报「使用混响等效果器、或者使用外部 VST 乐器时，音符停止或松开 MIDI 键盘，声音会突然
停止而不是自然消失」。先问清了三件事，用户的答案决定了这一批的形状：

| 问题 | 用户的选择 |
| --- | --- |
| 哪一种情况下被硬切 | **几种都有**（按停止 / 播放中音符结束 / 松开 MIDI 键盘） |
| 按停止时尾巴怎么办 | **自然放完** |
| 跳转与循环回卷 | **跳转截断；循环回卷不截断** |

### 两个根因

1. **`renderVoices` 的 `if (!active) continue;`。** 这句话的原意是「乐器没声音了就别白跑」，
   但它跳过的是**整条插入链与并入输出**——乐器最后一个声部的释音一结束，这一轨的混响 / 延迟
   就再也不被 `process`，尾巴当场消失。走带还在跑也一样，因为这条判断与走带无关。
2. **`AudioEngine::stop()` = 释放声部 + 把位置拨回播放起点。** 后半句在引擎眼里就是一个
   seek，于是 `applyPendingRequests` 里的 `effect->reset()` 会被执行——**每次按停止都把每条
   链的延迟线倒空**。同时释放走的是 `releaseAllVoices()` → 外部 VST 收到 **CC123
   all-notes-off**，很多插件收到它就立刻闭嘴，连自己的释音都不放。

### 改法

**链跟着尾巴走**（每槽一个 `chainSilenceBlocks`）：

- 乐器 `active` → 照旧渲染，计数清零；
- `!active` **且这条轨有插入效果器** → `trackBuffer.clear()` 之后**仍然** `runEffectChain` +
  `mixTrackIntoOutput`，并量这一块的峰值：`> 1e-5`（≈ −100 dBFS）就把计数清零，否则 +1；
  **连续 8 块**（512 帧 @48k ≈ 85 ms）全静音才回到 `continue`；
- `!active` 且**没有**效果器 → 立刻 `continue`（与以前完全一样，零开销）。
- 换轨 / 换链（`hostedEffects` 变化）时计数归零，不让上一条链的状态留下。
- 副作用（想要的）：尾巴放完之前，混音台上这根电平表会继续跟着落——它读的就是
  `mixTrackIntoOutput` 那一步。

**停止不再重置插入链**：`AudioEngine::stop()` 改走 `PlaybackEngine::setStopRewindSeconds()`，
它置一个 `pendingStopRewind` 再调 `setPositionSeconds`；音频线程在 `applyPendingRequests` 里
取到这个标记时，照旧 `releaseSustained()` / `releaseAllVoices(false)` /
`rewindControllerCursors()` / `lastMatched.reset()`，**只跳过 `effect->reset()`**。
用户跳转（拖播放头 / `Home` / 打开工程）保持原样：释放 + reset。循环回卷本来就只释放、不
reset，所以改完它自动就是「尾巴连着下一遍响」。

**外部 VST 用真正的 note-off**：`HostedInstrument` 新增 `virtual void releaseHeldNotes() {}`，
`HostedPlugin::releaseHeldNotes()` 对每个还按着的音符发一条**真的 note-off**（不发 CC123、
不 `channels.reset()`），并且**保留 `tailSamplesLeft`**，于是 `isActive()` 仍为真、插件继续
被渲染到尾巴放完。`allNotesOff()`（note-off + CC123 + reset）原样保留，仍然只用在换工程 /
卸载 / 槽位换乐器这种确实要立刻安静的场合。`PlaybackEngine::releaseAllVoices(immediately)`
按这个分岔：内置五种乐器照旧 `allNotesOff(immediately)`（`false` 本来就是「释放」），
外部乐器走 `immediately ? allNotesOff() : releaseHeldNotes()`。

试听那条路（松开 MIDI 键盘 / 音色窗口小键盘）本来就发真正的 note-off，所以它「松键就断」
完全是上面第 1、2 条造成的，**不需要为它单独写代码**。

### 测试

`Playback` 组新增 6 个子测试 / **12 条断言**（用与 `EffectChain` 组同一套假宿主乐器 /
假效果器替身）：

1. 「插入链跟着尾巴走：乐器静了，混响还在响」——渲染到乐器释音结束之后，断言效果器**仍被
   调用**、总输出里还有尾巴（RMS > 阈值）；
2. 「真的静下来之后，这条轨的链会自动停（不再空转）」——尾巴缩到 30 ms 再跑到静下来，总输出
   为 0 **且效果器不再被调用**；
3. 「没有插入链的轨：乐器静了就跳过（和以前一样）」——替身一次都收不到调用；
4. 「停止不 reset 插入链，跳转才 reset」——`setStopRewindSeconds` 之后 `reset()` 次数为 0，
   `setPositionSeconds(x)` 之后 ≥ 1；
5. 「停止 / 循环回卷给 VST 发的是 note-off，不是 all-notes-off」——`noteOff ≥ 1` 且
   `allNotesOff == 0`，且不挂音；
6. 「循环回卷不 reset 插入链（尾巴连着下一遍响）」——跨过循环点渲染，`reset()` 次数不变、
   乐器收到 note-off。既有的「跨越循环右边界的音符在回卷时被放掉，不会一直响下去」
   （D163）**继续通过**。

数字：单元测试 32 组 **2353 → 2365 条**（这一批只加 Playback 的 12 条）；离屏自检与快照

### 追加：再按播放会把尾巴掐断

用户接着要「再按下播放后，会掐断当前的尾巴」。这和上面并不矛盾，而是同一件事的另一半：
**停止**是「先听它落完」，**重新开始**是「上一遍已经结束了」。原来的行为是：按停止，尾巴响
着；再按播放，位置回到起点重新播，而那条尾巴**还压在下面继续响**——脏，而且让「停下来听
刚才那一下」变成了「再也不能干净地重放一遍」。

改法只有一处判断加一处动作：`AudioEngine::play()` 在**从停着开始**（`! isPlaying()`）时调
新增的 `PlaybackEngine::cutSoundingTails()`（消息线程只置原子标记），音频线程在
`applyPendingRequests()` 的末尾执行——**故意放在 seek 处理之后**，因为「停止的那次回卷允许
跳过链的 reset」，而「重新开始不允许」：

```cpp
releaseSustained();
releaseAllVoices (true);          // 硬放：外部插件收到 allNotesOff
for (auto& chain : hostedEffects) // 冲掉每条插入链（混响 / 延迟的尾巴）
    for (auto& effect : chain)
        if (effect != nullptr)
            effect->reset();
for (auto& blocks : chainSilenceBlocks)
    blocks = kChainSilenceBlocksBeforeStop;   // 链已经空了，不必再数那 8 块
```

两个细节值得记下来：

- **硬放而不是软放**：上一批为停止加的是 `releaseHeldNotes()`（真 note-off），但那是「让它
  自然落」；要「掐断」就得走 `allNotesOff()`（note-off + CC123 + `channels.reset()`）——软放
  留下的释音与插件自己的残响，正是这里要消掉的东西。
- **`isPlaying()` 那一问是必须的**：`play()` 不只从按钮进来（空格、混音台底部的 ▶、测试钩子
  都会调它）。如果不问，正在演奏时再点一下播放就会把所有发声的音符砍断——那是 bug，不是
  这个功能。

数字：`Playback` 组再补 1 个子测试 / 5 条断言，并给「停止 / 循环回卷给 VST 发的是 note-off」
那条**补了第 3 条**（再按播放时收到的确实是 `all-notes-off`，前面两条仍要求停止时
`allNotesOffCalls == 0`）；离屏自检补 2 项，真的走 `mixerAudio` 的走带：从停着按播放 →
掐断计数 +1，正在播时再点播放 → 计数不动，停止本身 → 计数也不动（**3 项**）。单元测试
2365 → **2371** 条，离屏自检 1184 → **1187** 项，快照仍 47 张；快照逐字节不变（这一批仍然
只有引擎行为）。

### 现状先摊开

- **右列没有自己的视图**：`yForHz` 是"把整组的频率范围等比铺满画布高度"（`lowestHz()` × 0.8
  到 `highestHz()` × 1.25），所以它永远是全览——想凑近看就只能换一组更窄的参考线组。
- **一个键只有一条线**：`midimap::Map::tile` 是 `vector<double>`、`free` 是 `map<int,double>`，
  一个键一个数字。想连第二个圆点，原来的代码是"把这一条换成那一条"（`setFrequency`）。
- **右键琴键已经在断开**，但只认"恰好落在键身矩形里"的点——黑键的键身只占那一行的左边
  约 62%，那行右边一截按下去**什么都不发生**，看起来就像"右键不管用"。

### 改法

**① 一个键 = 一组频率**（`Core/MidiInputMap`）：`tile` 变成 `vector<vector<double>>`、
`free` 变成 `map<int, vector<double>>`；API 分成**加**（`addFrequency`，重复的忽略）、
**减一条**（`removeFrequency`）、**清空这个键**（`clearFrequency`）与**替换**（`setFrequency`）。
内部一律"去掉 ≤0、排序、去重"，所以读到的永远是从低到高的一串；`frequencyFor` 返回最低的
那条（状态行、标题、老测试用的还是它），`frequenciesFor` 返回全部（引擎与录制用）。

- **播放**：`MainComponent::handleMidiMessage` 对每条线分配一个实时音符 id，
  `liveMidiNotes` 从 `map<int, HeldMidiNote>` 变成 `map<int, vector<HeldMidiNote>>`；
  松开时逐个 note-off，`releaseAllLiveNotes` 也一样（`getHeldMidiVoiceCountForTest` 就是
  "真的响了几条线"）。
- **录制**：`finishRecordedNote` 一个频率写一个音符（同一个起点 / 时长，仍是一条撤销记录），
  所以"听到的和录下来的是同一件事"。
- **工程格式两态兼容**：一条线时写数字（老文件的形状不变），多条时写数组；读的时候两种都认，
  0 依旧是"空"而不是"一条 0 Hz 的线"。

**② 右列自己的视图**（`UI/MidiInputWindow` 的 `MidiInputCanvas`）：新增 `groupZoom`
（0.5–8，1 = 全览）与 `groupScroll`（px），`yForHz` 在全览映射之上再套一层
`中心 + (拟合值 − 中心) × 缩放 + 滑动`。滚轮滑动（每格 48 px）、**Ctrl+滚轮缩放**、
**双击回全览**；缩放**以指针为锚点**——把指针下的那个"拟合高度"反算出来，缩完再放回指针下，
所以指哪放大哪。`clampGroupView` 把滑动夹在 `height/2 × (zoom − 1)` 之内：内容边缘最多贴到
画布边缘，既不会滑出画面，也不会出现半屏空白。栏首在非 1× 时写一行「×2.40　双击回到全览」。
滚轮的归属按**指针在哪一列**分：右列归它自己的视图，左列（非循环模式）照旧滚自己的音域。

**③ 右键分三层**：右键**一条连线**（点在线上，容差 6 px，按"点到线段"的距离算）只断开那一条；
右键**圆点**断开所有连到它的连线；右键**琴键**（改用与落点同一套"最近一行"规则，整行都算）
断开这个键的全部连线。左键拖过去仍然是"加一条"，所以同一个键连第二条线就是再拖一次。

## 第四十五批：修「多个音互相拉音高」（MIDI 通道分配 + 实时音符的 id 空间）（已完成）

用户报「用外部 VST 乐器时，同时响多个音会互相干扰，例如弯音轮只有一个音高是正常的」。问了两
轮把病根钉死：**单个音的音高是准的**（插件认 RPN 0、弯音范围没问题），坏的是**多个音互相拉**
——旧音的音尾滑到新音的音高上。读代码找到三条路径，都在宿主这一侧：

1. **通道回收太快**（"光放工程也不对"的原因）：`HostedPlugin::noteOff` 一发出就把通道还给
   `ChannelAllocator`，而 `allocate` **优先给最小号的空通道**。柱式和弦 B 于是立刻落在和弦 A
   刚放开的 0–3 号上，而插件还在那四个通道上把 A 的音尾放完——B 的 pitch bend 盖上去，A 的音尾
   就被拉到 B 的音高。连弹时每一遍都这样，听起来就是"几个音在互相拉"。
2. **实时音符与工程音符撞号**（"边放边弹"那一路）：工程音符的编号由 `buildSchedule` 每轨从 1
   开始发，MIDI 键盘的实时音符由 `MainComponent::nextLiveNoteId` **也从 1 开始**。两者同响时
   `allocate(noteId)` 觉得"这是同一个音"，于是两个音**共用一个通道**（一条弯音），而实时音的
   note-off 还会把工程音符的通道提前收掉——那个音从此再也收不到 note-off。
3. **抢通道时旧音还在响**：十六个通道用完时，原来的做法是"抢过来、被抢的音继续响，只是失去
   弯音"——它当然立刻走音。

顺带一条（修 1、2 会让音更分散地落在各通道上，这条就更显眼）：**踏板 / 表情是通道级状态**，
而每个音各在一个通道上，所以"先踩踏板、再起一个音"的那个音收不到踏板。

改法：

- `vst::ChannelAllocator` 每个槽多记一个 `released` 时刻，`allocate()` 变成
  **从没用过的优先（最小号）→ 释放最久优先**，全忙时取**占用最久**的那个并把它的音 id 报出来
  （`Allocation { channel, evictedNoteId }`）；`release()` 记下释放时刻，刚放开的通道不再是首选。
  四个音的柱式和弦连弹四遍正好用满十六个通道，而不是每遍压在 0–3 号上。
- `HostedPlugin::noteOn` 的顺序定死：**被抢的音先收（真 note-off）** → RPN 0（该通道没发过才发）
  → **补发记住的通道级 CC** → pitch bend → note-on。被抢的音迟到的 note-off 找不到通道，因此
  不会误杀新音（这一条也在自检里被计数验证）。
- 实时音符**翻译进私有负数空间**：`kLiveNoteIdBase = -(1LL << 40)`、`liveNoteIdFor(id)`，
  在 `PlaybackEngine::noteOnTrack / noteOffTrack` 里翻译。三个实时来源（键盘 1 起、MIDI 输入
  窗口试听 -1000 起、写音符试听 -100000 起）翻译后互不相同，也永远撞不到调度器的 1..N。
  放在引擎里而不是改三个调用点，是为了让这个不变量是**结构性**的。
- `HostedPlugin` 记住每个已转发控制器的最后一个值，通道**刚拿到音**时补发一遍（`reset()` /
  `prepare()` 清空；`allNotesOff()` 不清，踏板状态是插件自己的）。

测试用 VST3（`HMDAW/TestPlugin`）加了四个可读参数，让自检能直接看到"宿主做了什么"：
`Channel conflicts`（新音落在一个**已有音在响、且弯音不同**的通道上就 +1 —— 这就是"两个音高挤在
一个通道"的证据）、`Channels used`、`Pedal channels`、`Peak voices`，外加一个 `Reset counters`
让每个场景从零开始数。

数字：`Plugin` 组的通道分配断言改成新规则；`Playback` 组新增 1 个子测试 / 7 条断言（假乐器记录
收到的编号：工程音符 1 与实时音符 1 必须变成两个不同的编号）；离屏自检新增 8 项，全部走真
VST3：撞号场景**冲突 0 次 / 4 个音 4 个通道**、连弹四个和弦**用满 16 个通道 / 冲突 0**、
17 个音**收掉最老的 1 次 / 冲突 0**、踏板**落到 3 个通道**。单元测试 2417 → **2436** 条，
自检 1203 → **1211** 项，**47 张快照逐字节不变**。

踩到的坑记一笔：这一组的场景一开始放在「真 VST3」那一节后面，结果它**选中自己的 VST 轨、
清空工程**，把后面几张编辑栏快照（`34-piano-roll` / `35` / `40-panels-collapsed` / `42` / `43`）
全带偏了（每张上万像素）。改成把这一组**定义在插件节、执行在整轮最后**（`runChannelScenes`
这个 `std::function`），快照立刻回到逐字节一致——自检里的"探险"场景要么自己收尾干净，
要么就放到没有后来者的时候跑。

```

```

它做的事很小但决定性：加载那一个插件，在**两条通道**上用**两个不同的弯音**弹两个音（一秒之后

量本机**真实安装**的插件，结论很干脆：

| 插件 | 第一个音（440） | 第二个音（523.25 + 100 音分） | 结论 |
| --- | --- | --- | --- |
| **Serum 2** | **465.8 Hz**（被带走） | **553.7 Hz** | ✗ **整机弯音**：一条弯音把所有在响的音一起拉走；把它的 16 个 `Pitch Bend Chan N` 参数设满也没用 |
| **Pianoteq 9** | 440.9 Hz（没动） | 553.7 Hz | ✓ 按通道，弯音范围也正好是 ±2 |

也就是说：**整机弯音的插件，在 MIDI 层面没有任何办法**同时响两个不同音分的音——除非用插件

## 第四十六批：波表页的 3D 瀑布视图 + 实时光标 + 直接操作（已完成）

用户要「进一步开发波表合成器的操作与可视化」。问了三轮，选的是：**3D 帧瀑布 + 实时光标**、
**拖 / 点 / 滚轮直接操作位置**、以及**位置由引擎上报（不是界面自己算）**。最后一条是这一批
真正的分水岭——它决定了整个实现的结构。

### 为什么非得让引擎上报

顶部那条 88 px 的静态显示条原来是拿**参数**画的：它画的是 `osc.position` 滑块的值。所以拉大
「位置包络量」自动扫表时，**听到的波在扫、画面纹丝不动**——位置包络是逐声部在音频线程里推进的，
界面根本不知道现在响的是第几个声部、它走到哪了。顺带还有个更直白的错误：显示条**只认内置表**，
振荡器一旦指向自定义表，**画的跟听的就不是同一张脸**（用户的波表一张张全是自己导入的）。

所以这一批把位置**从下往上**接：`WavetableSynth` 在控制率分支算完 `v.position[o]` 之后，
把位置与「有没有声部」写进一组原子量（`Published{ position[2], voices }`）。
界面按 30 Hz 去读（`AudioEngine::getWavetablePosition / getWavetableActiveVoices`，**轨道声部
优先**；没有轨道声部时读预览声部的那一对，也就是屏幕键盘在试听的时候），拿它画光标。
这跟混音台的电平表是**同一套做法**：音频线程只写数字、不加锁，界面只读、不等待，读到的值最多
差一块（≈10 ms），对一根光标绰绰有余。光标只在有声部时刷新，静下来就停表、位置停在最后值。

两个当时没想到、编译/自检里撞到的细节，值得记下来：

- **`Published` 必须可拷贝 / 可移动。** 第一版直接写了
  `std::array<std::atomic<float>, 2> position;`——`std::atomic` 既不可拷贝也不可移动，而
  `PlaybackEngine` 把乐器放在 `std::vector` 里，于是 `WavetableSynth` 进不了容器，编译不过。
  （`std::atomic` 的默认构造也不是原子的"零"）。现在 `Published` 自带
  `copyFrom` / 拷贝 / 移动四个函数，逐个 `.load() / .store()`。
- **`voices` 必须写两次：`renderAdding` 的块首与块尾。** 只在块尾写的话，进了这一块又被调用方
  早早跳过的情况就漏了；只在块首写的话，声部**在这一块里**结束、之后调用方就不再来问它了——
  界面会永远显示"还在响"，光标永远停在最后那个值上不动。块尾那一次才是让"静下来"能被看到的。

### 视图本身

新的 `WavetableWaterfallView`（`Source/UI/WavetableEditor.{h,cpp}`，替掉原来的
`WavetableDisplay`）高 **168 px**：8 个帧从远到近堆叠（每往后一帧水平收缩 **3%**、纵向抬高
**6%** 画布高，振幅占 30%），每帧填充到中线 + 描边、左端标 `0…7` 帧号；**当前位置的波**用
`WavetableSynth::sampleTable`（与引擎共用同一个函数，也就是引擎真正在用的那条相邻帧插值）
算出来，画成一条 2 px 亮线——所以画面上那条亮线**就是此刻听到的波**，不是"照参数近似猜的"。
表按**实际使用的那张**取（`customTableId` 优先），顺手就把上面那个"只画内置表"的错误修掉了。
顶部窄条里是 **「振荡器 1 / 振荡器 2」**两个 84 px 切换，决定画哪张表、手势改哪个位置。

直接操作（都改**当前选中振荡器**的 `position`，一次手势一条撤销）：

- **上下拖动** = 连续改（指针 y 反解成 0…1，横向不参与；`beginParamEdit("改波表位置")` +
  拖动中 `pushParams`）；
- **点某一帧** = 跳到 `帧 / (帧数 − 1)`；
- **滚轮** = 每格 ±0.01；
- **双击** = 回到 **0.50**。

它们最后都落在 `position` 那个滑块上（走滑块自己的 `onValueChange`），所以**播放中拖位置能听到

渲染到了哪儿），逐次运行会差几个像素；交付里那份 `selftest.log` 是 0.143 / 114 → 108，
以它为准。单元测试 2450 → **2458** 条，自检 1217 → **1237** 项，快照 47 → **48** 张：
`29-wavetable.png`（这一页改版，**有意**变）、新增 `48-wavetable-3d.png`、
`41-mixer-playing.png`（历来运行间就会抖的那张），其余 **44 张逐字节不变**。

### 踩到的坑：别用 shell 改写源码

这一批中途出过一次真险：为了改一处 `WavetableSynth.cpp` 里的缩进，用了
`(Get-Content ...) -replace ... | Set-Content -NoNewline` 这种 shell 一行的写法。结果是**整个
文件的换行都没了**，一万多字符挤成一行——内容没丢，但 diff 全毁、警告行号全乱。
修的办法是：用 `apply_patch` 按原内容把整个文件重建，然后**把所有空白去掉、逐字节比较新旧**
（`-replace '\s',''` 之后长度与哈希都相同，10309 字符），确认"只是折行丢了"再继续。
**结论：源码一律只用 `apply_patch` 改**，shell 只用来跑构建、跑测试、比对文件。
