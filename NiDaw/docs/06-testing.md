# 测试与验收规范

## 三层验证

本项目不靠「能编译」当完成标准。任何功能都要经过三层：

| 层 | 目标 | 命令 |
| --- | --- | --- |
| 单元测试 | 领域数学、序列化、合成器 DSP、播放引擎的纯逻辑 | `cmake --build build --target NiDawTests` 后运行 `NiDawTests.exe` |
| 离屏自检 | 整个界面能构造、布局、绘制，并用合成鼠标事件驱动真实交互 | `"HM.exe" --selftest <输出目录>` |
| 手工验收 | 听感与手感（音高准不准、播放流不流畅） | 见每轮日志的验收记录 |

### 测音高的正确方法

用**线性插值后的零交叉**估算频率，不要直接数整数采样点的过零次数：
后者有最多半个周期的偏差，在 1 秒窗口上就是 ±0.5 Hz，正好卡在容差边缘。

另外要注意：**只有当 `fmDepth × fmRatio × 2π ≤ 1` 时相位才单调**，
此时零交叉测频才有意义；调制指数更大时音高由频谱决定，不能这样测。

外部插件是「一直活着的乐器」（第二十四批）：这条**必须用假的 `HostedInstrument` 在单测里测**，

- `CountingInstrument::active = false`（宿主没有任何音在响）→ 播放中渲染一块，
  断言 `renderAdding` **被调用过**、并且它的输出进了总输出（老代码会跳过它，计数是 0）；
- 走带**从未播放过**（`setPlaying (false)` 后直接渲染第一块）→ 同样断言被渲染、有声音，
  这是「不用先按播放就能试听插件键盘」的回归点（老代码只在跑过一次之后才用 `lastMatched` 渲染尾音）；
- 离屏自检里那三条守着窗口侧：界面尺寸记录跟着插件走（1200×320 → 400×300 都记录对）、

导出用的是「插件现在的状态」，不是工程里存的那份（第二十八批）：这是「导出的文件没有声音」
最常见的成因——一条 VST 轨的工程在插件加载之后没存过盘，`.nprj` 里的 `stateBase64` 就是空的，
离线实例于是按插件的**出厂音色**渲染，采样器（Kontakt 这类）的出厂音色就是空机架、也就是静音。
自检里这条是**对着声音测**的：真插件轨导出两次，中间把插件自带的音量从 0.5 拧到 0.25，
两次的干声 RMS 必须正好成 2:1（当前 0.1085 → 0.0543）；把 `runExport` 里的
`pluginHost.captureStates (project)` 注释掉，这条立刻变成 `0.1085 -> 0.1085` 而失败——
所以它不是「读了一遍代码觉得对」，而是真的守着这个行为。

导出的插件调用与导出日志（第三十一批）：自检跑完整导出之后断言
`PluginHostManager::getOfflineThreadViolationsForTest() == 0`——每一次「加载插件 → prepareToPlay
→ 还原状态」都在**消息线程**上完成（`runExport` 的工厂用 `MessageManager::callSync` 搬过去；

`render starting` / `capturing the live plugin states` / `offline instance for track N (…)` /
`offline instance ready` / `render finished: N file(s) written`（失败时是 `the render failed: …`）——
**每行都写在动作之前**，所以卡住之后最后一行就是卡在哪一步。

扫描的进程隔离（第二十九批）：`PluginScanProtocol` 单测管握手，自检管真的起进程——
一个内容是文本的 `.vst3` 扫出「0 个插件 / 1 个读取失败」；子进程按 `--scan-plugin-fail-for-test`
装死、按 `--scan-plugin-hang-for-test` 装卡（配 `setScanTimeoutForTest` 把超时压到 1.2 s）时，
HM 照常跑完并把文件记成失败。**这两个开关只影响子进程**（它自己退出 / 自己睡），
所以它们既能模拟坏插件，又不会让宿主做任何危险动作。

**预设库要指向临时文件**：自检一开始调用 `PresetStore::setDefaultFileForTesting(...)`，
把库落到输出目录的 `selftest-presets.json`，绝不碰真实的 `%APPDATA%\NiDaw\presets.json`。

**悬停类交互用合成的 `mouseMove` 驱动**：`PianoGrid::pointFor (hz, tick)` 把频率换成组件坐标，
再构造 `juce::MouseEvent` 调 `mouseMove`，最后用 `getRatioArrowBoundsForTest()` 断言箭头的位置
（上下边分别等于两条线的 y）与 `getRatioArrowLabelForTest()` 断言文字。诊断接口是**按需重算**的，
所以不必先截图再看——这也是它比"读上次绘制留下的矩形"更可靠的地方。
`getRatioArrowBoundsForTest()` 只包含**箭杆与箭头端**（不含文字板），所以「上边 = 一条线的 y、
下边 = 另一条线的 y」继续成立；文字板另有 `getRatioArrowLabelBoundsForTest()`，用来断言它居中于
箭头端、且**不包含鼠标点**（文字不能被指针压住）。悬停点要避开画布最左边缘（用 `tick = 1920`），
否则箭杆会被 10 px 的边界保护夹住，就测不出"箭杆跟着鼠标尖"这条。

**改了头文件必须换一个新的构建目录重编**：本机 Ninja 不跟踪头文件依赖，增量构建会留下按旧结构体
布局编译的目标文件，链接出来的程序表现是内存错乱（踩过两次：一次是编辑栏画到乐器栏上，
一次是把合成器数组搬上堆之后仍按 64× 大对象分配栈帧而栈溢出 `0xC00000FD`）。

**面板类断言要注意两件事**：一是参考线控制栏自己的颜色标记也用参考线颜色，
所以「隐藏后像素数为 0」这种断言要放宽成一个阈值；二是两个状态想要同一个频率时只有
**更靠上**的那条会被画出来（去重），测试里挑频率要避开同一个八度族（如 440 与 880 同族）。

**「控件有尺寸」不等于「内容画出来了」**：JUCE 里组件常常是先建好、再由父组件给尺寸，
所以「依赖自身尺寸算出来的几何」必须在 `resized()` 里重算，不能在 setter 里算一次就完事。
`AlgorithmDiagram` 就踩过这个坑——32 张缩略图在构造时尺寸还是 0×0，算法图库因此渲染成
32 个空方块；而当时「32 个格子都有真实尺寸」的断言照样绿。修好之后补了两条断言：
每张缩略图**内部的运算器方块**都非空、快照里方块描边的像素数达标（修前几乎为 0，修后约 49k）。

**点按钮要用「先翻转再加回调」的方式**：`TextButton` 的 `onClick` 不含状态翻转，
直接调 `onClick()` 会让 `getToggleState()` 还是旧值。测试辅助里的 `triggerMute` / `pressMute`
都是先 `setToggleState (! state)` 再调回调，跟真实点击一致。

**刻度对齐是「栏内」的要求，不是「栏间」的**（第二十三批改）：音轨栏的片段 / 标尺 / 节拍标记轨
必须用同一套映射，编辑栏的三根细条与画布也是；**两栏之间各自一套**，允许不同的缩放与偏移
（`TimelineView::arrangement / editor`）。自检里有两条对应的断言：音轨栏的标尺与片段 x 一致，
以及缩放编辑栏后音轨栏的片段 x **不动**。

**新增交互功能时，优先在自检里补一段合成鼠标事件的用例**——
这比手工点一遍可靠得多，而且能防回归。

**回归用例要复刻用户的真实操作序列，而不是挑一条最短的路径**：悬停比率箭头那条用例一开始只用
`mouseMove` 直接悬停，于是漏掉了「写完音符（= 一次拖动）之后箭头再也不出现」这个缺陷——它前面
最近的一次操作恰好是 `mouseDown`，顺手把拖动标志清掉了。现在改成合成完整的
`mouseDown` → `mouseDrag` → `mouseUp` 写一个音符、再切比率、再悬停，缺陷才会暴露。
用完记得把测试自己造出来的音符删掉、把选中态还原，否则后面的用例会被带偏
（这次就撞上了：多出来的音符让「静音后不产生事件」那条断言从 2 个事件变成 3 个）。

**自动滚动这类定时器行为，基线要在 `pump()` 之前取**：拖动一开始定时器就启动了，
而自检的 `pump()` 会真的让消息循环跑 60 ms，定时器于是偷偷滚上几步——先 pump 再记
「滚动前」的值，测出来的就是「滚动后 vs 滚动后」。同理，断言要留出**吸附网格**的余量：
一步滚动只有约 82 tick，而吸附单位是 960 tick，跑满 24 步（约 1900 tick）才保证跨过一格。

**鼓格视图要按行取点，不要按频率**：鼓轨没有频率轴，所以诊断接口提供
`getDrumRowCountForTest()` / `getDrumRowBoundsForTest(i)` / `pointForPadForTest(pad, tick)` /
`padForPointForTest(point)`，自检用它们合成鼠标事件。力度亮度用**采样音符矩形内部的平均亮度**
断言强弱不同，比数某一个颜色更稳。

**手势按方向分流后，「拖动」和「单击」都要各自断言一次**：可写位置（鼓垫行 / 参考线 ±6 px）
起拖时，横向为主写音符、竖直为主框选，所以每个用例都要同时证明三件事——竖直拖动**没有写出音符**
（比对拖动前后的音符数）、竖直拖动**确实选中了**它覆盖的音符、横向拖动**恰好写一个**音符且
`pad` / 长度正确。只断言其中一半会出现「框选生效但顺手写了一个音符」这种回归漏网。
方向的判据在测试里要留出余量：横幅别做得接近正方形（鼓格用例把 `pixelsPerQuarter` 调小、
再让竖直跨度明显大于水平跨度），否则主轴判定会随画布尺寸翻转。

### 写像素计数断言的注意点

- 颜色要选**只有该元素使用**的。例如 `0xffe6e6ee` 只用于小键盘白键。
- 注意 alpha 混合：半透明绘制出的实际像素不等于目标颜色，容差要放宽，
  或者干脆把该元素改成不透明绘制（参考线就是这么改的，同时也修好了发虚的问题）。
- 断言阈值只保证「确实画出来了」，不要卡得过紧，否则改个尺寸就红。
- **裁切类 bug 用「两张快照逐像素比对」比数颜色可靠**：比如验证「滚动后片段不会画到音轨头上」，
  就在 `horizontalOffsetTicks = 0` 与 `= 960` 两种状态下各截一张音轨栏快照，
  断言音轨头那块矩形**逐像素完全相同**。用颜色计数反而会被音轨头本来就有的色条干扰；
  逐像素比对没有这个问题，而且不依赖具体配色（这条测试在去掉裁切后立刻报出 10706 个差异像素）。

## 测试环境的坑

### 零警告是构建的一部分

`work\build_app.bat` 与 `work\build_tests22.bat` 在构建之后会扫自己的日志：只要出现**指向
`NiDaw\Source\` 的 `warning C`**，就打印出来并让构建失败（`WARNINGS_IN_SOURCE_CODE`）。
外部 `external\JUCE` 的警告不算。这样警告不会悄悄涨回来（第二十五批之前积到了 84 条）。

**闸门自己的写法也有坑**（第二十九批踩到并改掉）：原来写成
`findstr /C:"warning C" log | findstr /C:"\Source\" > out`，两个问题叠在一起——
（a）**管道后面那个 `findstr` 的退出码没有被 `if errorlevel` 读到**（管道里第一条命令的结果
才是关键，而且第二条在没输入时也会「成功」），（b）**模式以反斜杠结尾、紧跟着一个引号**时，
在 cmd 里不会原样传进去。结果是第二十九批往 `SelfTest.cpp` 里加了 5 条 `C4456`
而构建照样打印 `BUILD_OK`。现在拆成两条、不要管道：
`findstr /C:"warning C" log > warnings.txt` 然后
`findstr /L /C:"NiDaw\Source" warnings.txt > source-warnings.txt`（**结尾不要反斜杠**）。
改完拿一份**真的有警告**的日志试过：`source-warnings.txt` 里出现 5 行，构建才会失败。

### 等价重构要用「逐字节相同」来验收

重命名、搬文件、抽公共函数这类**不改变行为**的改动，光看断言数字不够：数字一样不代表输出一样。
可靠的做法是把改动前的产物留一份基准，然后逐字节比对：

- `selftest.log`（951 行 `-- 段落` 与 `ok …` 文本，没有文件行号）应当**完全相同**；
- `screenshots\` 里 38 张 PNG 的**文件名与内容**都应完全相同；
- 单元测试的**逐组通过数**应完全相同。

第二十五批就是用这个办法抓到了机械改名「改到字符串里」的问题：某次改名把
`30-drums-grid.png` 改成了 `30-drums-sectionGrid.png`、还把 6 条断言的文字改了——
断言数字与像素快照都没变，只有日志文本变了。**这类问题只有逐字节比对能发现。**

### 自检里不要读「定时器跑过之后」的值

拖动到边缘的自动滚动测试是个反例：原来它先 `pump()` 再读基线、又 `pump()` 再读结果，
而**自动滚动的定时器会在这两次 pump 里各跑几步**，于是记录下来的 tick 数取决于机器负载
（同一份二进制两次运行分别是 `164.571 -> 1316.57` 和 `82.2857 -> 1234.29`）。
现在这两条用例都在**拖动之后立刻读基线、手工跑完立刻读结果、中间不 pump**，
数值只来自手工步数，两次运行逐字节一致。

### `Path::getNearestPoint` 返回的是「沿线的位置」，不是「距离」

旋律生成器画布上「右键点在电缆上就拔掉它」的命中测试一开始写成：

```cpp
if (path.getNearestPoint (point, nearest) < 7.0f)   // 错
```

JUCE 的头文件注释说它给出「离目标点最近的那一点」，但**实现返回的是 `bestPosition`** ——
最近点**沿电缆走了多远**（`juce_Path.cpp` 里就是 `return bestPosition;`）。于是判据变成了
「离电缆**起点** 7 px 以内」，而不是「离电缆 7 px 以内」：点在电缆正中间时算出来的「距离」
是这条电缆长度的一半，反而不命中；而另一条起点离指针很近的电缆被命中——用户看到的就是
「右键点这根线，掉的是另一根」。

正确写法是把最近点**自己要回来**再量距离：

```cpp
path.getNearestPoint (point, nearest);
const auto distance = nearest.getDistanceFrom (point);
```

这条 bug 是靠**自检里带诊断信息的断言**抓到的：失败消息里带上「哪根线被拔掉了、两条线的
包围盒、点在哪」之后，一眼就看出「点落在 2>4 这条线上，被拔掉的却是 4>5」。
**断言失败时把关键数字写进消息**（这一批新加的断言都这么做）比回来加断点快得多。

### 中文字面量的扫描必须先把 NI_TXT 抠掉

`juce::String (const char*)` 只认 ASCII，所以源码里的中文必须包 `NI_TXT`。用「这一行里有没有
`NI_TXT`」来扫描是**不够**的：`{ NI_TXT ("三角"), "正弦" }` 这种一行里的漏网之鱼会被整行放过
（真出过一次：减法合成器的波形下拉里「正弦」显示成乱码）。正确的扫法是先把 `NI_TXT (...)` 与
`juce::String::fromUTF8 (...)` 整段替换掉，再找剩下的中文：

```
rg -n --pcre2 '(?<!NI_TXT \()"[^"]*\p{Han}' Source
```

（预设库那种 `const char*` 名字是有意为之：它们统一经 `juce::String::fromUTF8` 读出来，
和 `FmPresets.h` 一个写法，所以扫描结果里剩下的是这一批，属正常。）

- 测试进程可能因界面代码而挂起。跑测试时**务必带超时**，不要裸跑等它自己结束。
- 不要用 `findstr /C:"error"` 过滤构建日志——`jerror.h` 这类文件名会误命中，
  要用 `findstr /C:": error "`。
